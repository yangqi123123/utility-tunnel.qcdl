# IoT 方案与原型说明

## 1. 文档定位

本文件用于产品排版和技术评审。本阶段只确定信息架构、页面入口、核心字段与交互关系，不接真实接口，不创建后端模块。

静态原型：[`iot-console-prototype.html`](../../../frontend/apps/prototype-antd/public/iot-console-prototype.html)

## 2. 方案结论

IoT 管理台不以“采集器”为中心，而以一次外部系统接入和设备能力模型为中心：

```text
接入系统 -> 连接配置 -> 协议驱动 -> 设备 -> 物模型 -> 点位映射 -> 采集/控制 -> 数据与事件
```

四个概念必须分开：

- **协议驱动**：负责 HTTP、MQTT、Modbus、OPC UA、BACnet 的连接和收发。
- **厂商适配**：负责海康、科拓、GVS、安科瑞等认证、报文和回调语义。
- **物模型**：定义属性、事件和服务，表达业务含义。
- **点位映射**：把 JSON 字段、MQTT Topic、寄存器、OPC UA NodeId 映射到物模型。

因此“温度”不应该写成 Modbus 地址或 JSON 路径；协议细节只能存在于点位映射。

## 3. 页面菜单

| 一级菜单 | 页面目标 | 首期重点 |
| --- | --- | --- |
| IoT 总览 | 查看接入、设备、采集率、告警和近期事件 | 必须有 |
| 接入管理 | 管理厂商系统、连接、认证、环境和协议 | 必须有 |
| 设备管理 | 注册设备、绑定接入、查看在线状态和位置 | 必须有 |
| 物模型 | 管理产品类型、属性、事件、控制服务 | 必须有 |
| 点位映射 | 配置 HTTP 字段、MQTT 字段、寄存器与属性的关系 | 必须有 |
| 采集任务 | 配置轮询、订阅、回调、频率、重试和批量读取 | 必须有 |
| 运行监控 | 查看连接、采集任务、报文、失败和延迟 | 必须有 |
| 指令中心 | 查看控制任务、下发、确认、超时和审计 | 必须有 |
| 告警事件 | 查看设备故障、离线、越界和厂商告警 | 必须有 |

原型首页采用工作台布局：左侧菜单、顶部上下文栏、四个运行指标、接入状态表、设备状态表、快捷入口和运行事件时间线。

## 4. 配置流程

### 4.1 新增接入

产品操作顺序：

1. 创建外部系统接入，例如“科拓智慧停车正式环境”。
2. 选择传输方式：HTTP、MQTT、TCP、串口等。
3. 选择具体协议：HTTP JSON、MQTT、Modbus TCP、Modbus RTU、OPC UA、BACnet/IP。
4. 配置地址、端口、认证、超时、重试和环境。
5. 测试连接，保存后进入接入详情。

### 4.2 创建物模型

1. 创建产品类型，例如“智能电表”“道闸设备”“照明回路”。
2. 增加属性：数据类型、单位、读写权限、范围和精度。
3. 增加事件：设备故障、通行记录、停车入场等。
4. 增加服务：开闸、开门、开灯、设置温度、播放广播等。
5. 发布物模型版本，已绑定设备使用明确版本。

### 4.3 注册设备与配置点位

1. 注册具体设备，填写设备编码、名称、厂商、位置和所属接入。
2. 绑定产品/物模型。
3. 配置原始数据来源。
4. 选择目标属性、事件或服务。
5. 配置解析规则：JSONPath、Topic、寄存器地址、数据类型、字节序、缩放、偏移、枚举和质量规则。
6. 在线测试一条数据，预览“原始值 -> 统一值”的结果。

## 5. 运行流程

### 5.1 上行

```text
轮询/订阅/回调
  -> 原始报文
  -> 厂商适配
  -> 点位解析
  -> Telemetry / Event
  -> 最新状态
  -> 历史数据
  -> 告警和业务事件
```

### 5.2 下行

```text
业务请求
  -> 校验设备、服务和参数
  -> 创建指令任务
  -> 物模型值转协议值
  -> 协议驱动发送
  -> ACK/回调/状态回读
  -> 成功、失败或超时
  -> 审计记录
```

## 6. 原型交互范围

- 顶部“新增接入”“注册设备”打开同一套配置抽屉，演示字段布局。
- 快捷入口分别打开接入、物模型、点位映射抽屉，或触发一次采集提示。
- 接入表的“详情”按钮显示静态反馈。
- 左侧菜单可切换选中状态，后续可以直接扩展为真实路由。
- 保存按钮显示“静态演示”反馈，不写入数据库。

## 7. 后续页面拆分建议

### 接入管理

列表字段：接入名称、厂商、系统类型、传输方式、协议、环境、连接状态、最近通信、设备数、操作。

详情页建议使用页签：基本信息、连接配置、接口目录、设备列表、原始报文、运行日志。

### 设备管理

列表字段：设备名称、设备编码、产品、所属接入、网关、位置、在线状态、最后上报、告警数、操作。

详情页建议使用页签：设备概况、实时数据、物模型、点位、采集任务、指令记录、事件告警。

### 物模型

建议采用左侧产品树 + 右侧三页签：属性、事件、服务。属性编辑器必须支持数据类型、单位、读写权限、值域和描述。

### 点位映射

建议采用“设备/产品选择 + 点位表 + 右侧映射抽屉”。抽屉显示原始来源、解析规则、目标物模型、测试输入和测试输出。

## 8. 本阶段不做

- 不接真实 API、MQTT Broker 或工业设备。
- 不在页面阶段决定最终时序数据库。
- 不实现动态脚本解析、规则引擎和插件市场。
- 不把现有旧项目的表结构直接复制到新模块。

## 9. 产品评审需要确认

- 首页更偏“平台运维”还是“楼宇设备运营”。
- 菜单是否需要按“接入配置”和“设备运行”分组。
- 设备详情是否要展示楼栋、楼层、空间树。
- 控制操作是否需要二次确认、审批或双人复核。
- 原始报文是否允许普通运维人员查看。
- 告警是否需要确认、屏蔽、升级和关闭流程。
- 是否需要单独的网关页面，还是网关仅作为设备拓扑中的一种节点。

## 10. 验收标准

- 产品可以打开静态 HTML 看到完整菜单和首页布局。
- 新增接入、注册设备、创建物模型、配置点位映射均可打开抽屉。
- 取消、关闭、保存反馈可正常使用。
- 桌面端和窄屏下无主要内容重叠。
- 方案中的接入、设备、物模型、点位、采集和控制概念在页面上有明确入口。

## 11. HTTP 接口配置原则

HTTP 接入不能只配置一个 URL。建议拆成三层：

    接入系统
      -> HTTP 连接配置
          -> API 接口目录
              -> 请求参数 / 认证签名 / 响应映射

### 11.1 HTTP 连接配置

连接配置只保存接口之间共用的内容：

- Base URL
- 公共请求头
- 认证方式
- AppId、AppSecret 或 Token
- 签名算法
- 连接超时

### 11.2 API 接口配置

每个接口单独配置：

- 接口名称和编码
- 请求方法
- 请求路径
- 接口用途：采集、查询、控制、事件确认
- 请求格式
- 设备识别字段
- 请求参数
- 响应数据映射
- 接口级超时和失败处理

请求参数至少需要包含：

| 字段 | 示例 |
| --- | --- |
| 参数名 | deviceCode |
| 参数位置 | Header、Query、Path、Body |
| 数据类型 | STRING、INTEGER、BOOLEAN、OBJECT |
| 是否必填 | 是 / 否 |
| 参数来源 | 固定值、接入配置、设备编码、用户输入、上一步响应 |
| 默认值/示例值 | gate-001 |
| 转换规则 | 日期格式、枚举转换、值域校验 |

### 11.3 响应数据映射

响应映射负责把厂商返回结果转换成统一结果：

    $.data.list[*].deviceCode -> 设备识别
    $.data.list[*].power      -> active_power
    $.data.list[*].status     -> device_status

响应映射还应配置：

- 成功判断路径和成功值
- 错误码路径和错误消息路径
- 数据列表路径
- 分页字段
- 设备识别字段
- 物模型属性/事件目标
- 单位、枚举和数据转换

### 11.4 重试策略的归属

重试分三层，不能只放一个“系统重试策略”：

| 层级 | 负责内容 |
| --- | --- |
| 连接层 | TCP/HTTP 连接超时、连接失败、MQTT 重连；属于协议驱动运行参数，不作为接入表单中的业务策略 |
| 接口/任务层 | 某个采集接口或采集任务的调用超时、重试次数、失败后保留上次值或触发告警 |
| 指令层 | 控制下发超时、重试次数、ACK/回调/状态回读确认 |

例如 HTTP 查询接口返回 200 但业务码失败，不能按网络重试策略直接判断成功；应先按响应映射判断业务成功，再决定是否重试。
